CANDIDATE TRACKER WEB COMPONENT REFACTOR PLAN

Status: planning only
Scope: web/src React components and CSS ownership
Out of scope: API behavior, routes, domain rules, backend changes, and adopting a third-party UI/CSS library

GOALS

1. Preserve current behavior and visual design.
2. Remove exact duplication before introducing new abstractions.
3. Keep route pages focused on loading data and composing the screen.
4. Keep feature-specific components with their page feature.
5. Put only genuinely reusable UI in a shared components directory.
6. Split the 2,187-line App.css by ownership without changing selector behavior.
7. Avoid speculative abstractions, barrel files, and generic components with excessive props.

COMPONENTS THAT SHOULD NOT BE COLLAPSED

1. StatusCell should not become StatusBadge. It has table-specific dot styling and stage-specific labels.
2. BasicCommentModal should not merge with InterimUpdateModal. Their data ownership and save behavior differ.
3. ProjectFormModal should not merge with LogContactAttemptModal. They only share a modal shell.
4. ProjectCard should not become a generic Card. Its status, routing, candidate count, and edit rules are domain-specific.
5. InternalNotes and ActivityHistory should remain separate. They have different data rules and interaction patterns.
6. QuickActions should not be turned into a generic menu. It contains candidate workflow rules.
7. Page-specific form sections should not be extracted merely because they use section/label markup.
8. Link and button elements should not immediately be forced into one polymorphic Button component. Preserve correct HTML semantics first.

CSS PLAN

Current state:
- index.css: 31 lines of global document styling.
- App.css: 2,187 lines containing app shell, projects, pipeline, candidate detail, modals, controls, and responsive rules.
- Repeated values include white backgrounds, 12/14px font sizes, 4/6/8px radii, 8/10/12/16px gaps, and several repeated text/border colors.
- Existing class naming already uses useful base/modifier patterns such as status-badge--success and project-card--new.

Target ownership:

1. web/src/index.css
   - Browser reset and body/root defaults only.
   - Import tokens and shared controls before application/page CSS.

2. web/src/styles/tokens.css
   - Repeated colors, spacing, font sizes, radii, and shadows.
   - Start only with values that have repeated semantic meaning.

3. web/src/styles/controls.css
   - Existing shared button/link control classes such as primary-button, secondary-button, danger-button, outline-button, and dark-button.
   - Keep native button and Link semantics; share appearance through CSS.

4. web/src/app/App.css
   - App shell, sidebar, top bar, breadcrumbs, account controls, and main layout only.

5. ProjectsPage.css
   - Project grid/cards and project form styling.

6. ProjectPipelinePage.css
   - Pipeline title, stage tabs, table, stage comments, and table-cell presentation.

7. CandidateDetailPage.css
   - Candidate layout, notes, activity, quick actions, contact forms, and candidate-specific modal content.

8. Shared component CSS
   - RouteModal, StatusBadge, Avatar, SearchField, and feedback styles may be colocated as same-name CSS files under their component folders.

CSS library decision:
- Do not add a full CSS framework or component library during this refactor.
- The current UI is custom and already substantially implemented.
- First establish internal reusable primitives and CSS ownership.
- Reassess an unstyled accessibility library later, especially for dialogs and menus.

NAMING AND EXPORT RULES

1. React component files use PascalCase.tsx.
2. Page directories remain kebab-case.
3. Route components end in Page.
4. Route-driven modal shell is named RouteModal to describe its URL-based close behavior.
5. Shared components expose one clear component; avoid index.ts barrel files.
6. Small components used only by one owner remain private in that owner's file.
7. Feature-specific components are not placed in the global components directory.
8. Generic names such as Card, Panel, Wrapper, or Container are avoided unless the abstraction has a stable semantic contract.

IMPLEMENTATION PHASES

Phase 1: Baseline and exact deduplication
- Record current route behavior and key screen states.
- Add RouteModal, StatusBadge, and Avatar.
- Replace duplicate implementations without changing layout or business logic.
- Build and lint.

Phase 2: Mechanical page decomposition
- Move existing local components into the target feature files.
- Keep props and behavior unchanged.
- Introduce PipelineTable and CandidateHeader as cohesive extractions.
- Move private helpers only with their owning components.
- Build and lint after each page.

Phase 3: Repeated feedback and search UI
- Add SearchField, LoadingState, ErrorMessage, and EmptyState.
- Preserve page-specific modifier classes through className props.
- Verify labels and accessibility semantics.

Phase 4: CSS ownership split
- Move selectors from App.css into app, shared, and page stylesheets.
- Preserve CSS import order and specificity.
- Introduce a small token set for proven repeated values.
- Remove only selectors proven unused after visual checks.

Phase 5: App composition
- Move Breadcrumbs and DevAccountSwitcher.
- Extract AppRoutes.
- Keep App responsible for session bootstrap and shell composition.

Phase 6: Verification
- npm run lint
- npm run build
- Smoke-test every route and route-driven modal.
- Compare desktop and responsive layouts.
- Check loading, error, empty, disabled, and role-specific states.
- Check modal keyboard behavior and focus before claiming accessibility improvements.

RISKS AND CONTROLS

1. CSS order/specificity regressions
   Control: move selectors mechanically before changing values; preserve import order.

2. Behavioral changes while moving QuickActions
   Control: move code first, redesign later; keep transition helpers and props unchanged.

3. Over-generalized shared components
   Control: only share exact repeated semantics; keep domain components feature-local.

4. Circular imports
   Control: shared components import no page code; pages may import shared components.

5. Router modal regressions
   Control: RouteModal retains closeTo and Link-based close behavior during initial extraction.

6. False reuse through generic Button/Card components
   Control: retain CSS classes and native elements until behavior, not only appearance, is demonstrably repeated.
