# Backend Model

## Required Entities

`User`

Stores identity, role, active state, and external auth subject.

`Project`

Stores the open role: name, position, status, notes, created date, archived date, closure data, and member assignments.

`ProjectMember`

Connects users to projects. A project can have multiple HR users and multiple hiring managers.

`Candidate`

Stores person-level data: name, source, LinkedIn profile, phone, email, resume, and sync metadata.

`CandidateApplication`

Stores a candidate inside one project: project id, candidate id, current stage, current status, imported date, offer priority, offer dates, final closure reason, and duplicate warning.

This is the main workflow record. Stage and status should live here, not on the person-level candidate.

`File`

Stores file metadata and, for the first version, file bytes in Postgres.

`Interview`

Stores scheduled interview details for one candidate application: type, date, time, timezone, meeting URL, scheduling status, and reschedule history.

`CandidateNote`

Stores structured or free-text notes, author, author role, visibility, created date, and candidate application id.

`ContactAttempt`

Stores outreach attempts: candidate application id, context, result, attempted date/time, notes, created by.

`CandidateActivityEvent`

Stores the visible audit trail. It should be generated by backend actions.

`RejectionFollowUpTask`

Stores rejection follow-up eligibility and handling: candidate application id, eligible date, status, contact attempts, handled date.

`ProjectOfferQueueItem`

Stores offer priority for a candidate application inside a project.

`Offer`

Stores actual offer attempts and outcomes.

`ExternalReference`

Stores provider-specific external ids for projects, candidates, and other records. This keeps LinkedIn and future integrations out of core tables.

## Derived Values

Project candidate count is derived from candidate application records.

Project `candidate_accepted` display state is derived from an active project with an accepted offer.

Rejection follow-up rows come from `RejectionFollowUpTask`, not from candidate status alone.

Offer rank comes from `ProjectOfferQueueItem` records.

External provider ids come from `ExternalReference`, not direct provider-specific columns on core records.

## Visibility

HR can see all notes, including `hr_only` fields.

Hiring managers cannot see `hr_only` notes or note fields.

Rejected, withdrawn, and offer-rejected candidates should not show normal quick actions. Rejection-source detail can show rejection-specific actions.
